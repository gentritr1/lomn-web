# M2a-1 — Script VM core, Python oracle, conformance corpus, differential run: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a C++ `lomn::osi::Vm` and an independently written Python oracle that agree byte-for-byte on:
- a conformance corpus authored from the citation tables;
- the real `Base.osi` (`Setup` plus 600 `Process` frames plus keys, with typed stubs) on native, wasm32 and Python.

**Architecture:** the VM follows `docs/osi/opcodes.md`. Values are 8-byte tagged variants holding handles, never pointers (D7). Natives come from `data/osi/natives.json` plus a mods table through a pluggable registry, and a fixed-format text trace records every step. The oracle is written by a different agent, from the tables and the cited asm, never from the C++. Corpus expectations are computed from table rows by a non-interpreting calculator. The differential run compares trace digests across native, wasm32 under node, and Python.

**Tech stack:** C++17 (the existing CMake targets, doctest), emscripten wasm32 under node, Python 3 (stdlib only for the oracle), GNU make.

**Spec:** `docs/superpowers/specs/2026-10-08-lomn-web-m2-design.md`: §5 (oracle), §7 (M2a-1, A5–A7), and rulings D1–D12. **Design source:** `docs/knowledge/research/2026-10-08-m2a1-design-consult.md`. Sections are cited below as "consult §x". The interfaces in consult §1.2–§1.3, the trace format in §2 and the corpus format in §3 are normative for this plan, except where a ruling below overrides them.

## Global constraints

- Never run the game's `.exe` or `.dll`. Read them as data only. Never commit game data, renders, decompiled code blocks, or `.osi` binaries assembled from the corpus (commit the `.asm` source only).
- No foreground command over about 2 minutes. Builds, test suites, the corpus and the A6 run go in the background, with a wait that exits on success, on failure, and at a deadline.
- zsh: quote globs and words that start with `=`. Never execute an unquoted `$VAR` holding arguments.
- `opcodes.md` is generated and also hand-authored: regenerate over the committed file, never delete it first.
- Every number a test pins must come from a command run in the task, and that command is named in the commit body.
- Scratch helpers go in a private per-task subdirectory of the session scratchpad.
- **Independence:**
  - The oracle (Task 3) and corpus authors (Tasks 4–5) never read `engine/src/osi/`, `engine/include/lomn/osi/`, `engine/tests/test_osi_vm.cpp`, `engine/tools/lomn_osi_*`, or each other's in-progress output.
  - The C++ author (Task 2) never reads `tools/research/osi_vm.py` or `tests/osi/conformance/`.
  - Each of those tasks runs in its own worktree, cut from Task 1's commit.
- Never push, amend, rebase or stash. Never dispatch subagents. Commit only the task's files.

## Review focus

1. **Float bits.** A mixed int/float result that differs only in the last f32 bit (D8). Every arithmetic path prints f32 bits in traces and expectations, never decimal text.
2. **Alloc/free order.** Dispose order (`F` lines) differs between C++ and Python even when counts match. Corpus traces are compared byte-for-byte, not by counts.
3. **Native argument re-entrancy.** A native that re-enters the VM corrupts the outer frame. Covered by the `t.reenter` program.
4. **Patching.** The script image must never be written (D4). A sha256 tripwire runs at the end of every run.
5. **Error snapshot.** The error snapshot must be taken before any reset (D10). Expectations assert the state at the throw.

## Rulings on the consult (controller)

- R1: D7–D12 are ratified in the spec.
- R2: the E2 matched pair is Task 4 (corpus group A) → Sonnet and Task 5 (group B) → Opus-medium. The consult measured the groups within 3 % on every axis (M24).
- R3: Task 6 (the differential run) goes to the Task 2 author (agent V) only if V is still resumable. Otherwise it goes to a fresh Opus agent with the Task 2 report.
- R4: Task 7 (mutation) must be run by an agent that wrote neither the VM nor the oracle.

## Order and parallelism

1. Task 1 runs first.
2. Tasks 2, 3, 4 and 5 then run in parallel, each in its own worktree from Task 1's commit:
   - Task 2: `lomn-web-m2-vm`
   - Task 3: `lomn-web-m2-oracle`
   - Task 4: `lomn-web-m2-ca`
   - Task 5: `lomn-web-m2-cb`
   
   The controller cherry-picks each one after its review.
3. A5 gate: `lomn_osi_conform` and `osi_vm.py --conform` are both N/N on the merged corpus. Each disagreement is resolved by going back to the asm, never by a vote. The fix goes to whichever side the asm proves wrong, and a table fix goes to `opcodes.md` with a citation.
4. Task 6 runs after A5 passes.
5. Task 7 runs after Task 6.

**Reviews:** every task gets a blind Opus review (a diff-only package) and frozen-copy controller verification. The final whole-branch review is done by Fable.
