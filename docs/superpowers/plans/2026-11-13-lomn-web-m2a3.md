# M2a-3: menu systems (the main menu renders natively and as wasm32): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `lomn_view --script 1` runs `Base.osi` past `Setup` into the **active** main menu and renders it: the `lev0/frnt` area seen through the script's camera spline, then the HUD (tile-font text, HUD sprites, the cursor) drawn through the D3D8 shim after the area. This must hold:
- natively and as wasm32, with a null-backend state log that is byte-identical across the two (A12) and equal to an expected sequence written independently from the cited render functions;
- with every native the menu run reaches at tier 1 or tier 2 (A10 extended to the menu run), the host's engine → script events (`OnEvent(6)` from the camera, `OnEvent(26/23/24/25)` from the mouse, the keys) modelled in both engines;
- with the frames rendered at 640×480 and the owner's second resolution, ready for a pixel comparison against the owner's screenshots of the original (A13, owner-gated).

**Architecture (unchanged where it works):** M2a-2's VM, native framework, `ScriptHost` and both engines stay. New pieces:
- **Host sources** in both engines: the camera process (spline follow, `OnEvent(6)`, sway), the mouse driver (`OnEvent(26/23/24/25)`), the existing keys, ordered as the original's process map orders them. They write the `C -1` records D14 reserved.
- **INI** (`Bionicle.ini` through the VFS) with Win32 `GetPrivateProfileStringA` semantics, in both engines.
- **HUD object state** (sprites, text objects, fonts, the HUD director's list and visibility) modelled in both engines and compared through a new state-snapshot record.
- **Rendering** (C++ only, with an independent Python oracle of its state log, as in M1): tile fonts from the binary `.fnt` inside the `.col`, HUD sprite textures, the HUD draws through `lomn::d3d::Device8` (FVF, HUD transform, states), composed after the M1 area frame.

**Tech stack:** C++17 (CMake, doctest), emscripten wasm32 under node 20, Dawn/WebGPU natively (Metal), Python 3 stdlib for the oracles, GNU make. Read as data only: `/usr/bin/objdump -d --x86-asm-syntax=intel` on the install exe, `gen/decomp`, the install's `.col/.fnt/.tga/.slb/.blk` files and `Base.osi`.

**Spec:** `docs/superpowers/specs/2026-10-08-lomn-web-m2-design.md` §3.5–3.7, §7 (M2a-3 row; A11, A12, A13, A15), §8 risk 3, §9, rulings D1–D16. **Contracts this plan extends:** `docs/osi/natives.md` (§4, §6.2, §6.3, §7, §8.2, §9), `docs/osi/trace.md` §6 (D14 `C -1`), `lomn/d3d/device8.h` (the A9 state-log grammar of M1a-3). **Precedent:** the M2a-2 plan and its Fable review (C3 there: a plan built on an unmeasured timer premise). This plan's own premise (the menu needs the camera's `OnEvent(6)`) is measured below, not assumed.

## Review focus (failure modes no task's own tests cover, and the pin for each)

1. **A shared misreading of the spline.** "Cubic spline" can be natural, clamped, Catmull-Rom or Hermite with stored derivatives; knot times can be normalised or absolute; the 4.0 can be a duration or a speed. Both engines reading one decomp line the same wrong way would agree and both be wrong.

## Decisions (the controller rules on each; recommendation first)

1. **SDL3 input.** *Recommend:* **defer SDL3.** M2a-3's input is a host-side `InputState` fed by deterministic replay (KEYSPEC plus a new MOUSESPEC, Decision 4) natively, and by browser events in M2b. No acceptance row (A11–A13, A15) needs an interactive native window, `lomn_view` is headless, and SDL3 is a new third-party dependency in the toolchain. *Alternative:* add SDL3 to the native build now for an interactive `lomn_native` window. *Cost if wrong:* one later task (a thin SDL3 → `InputState` adapter); the mapping table (probe 3 "Mapping for the port") is shared either way.
2. **The deterministic menu runs.** *Recommend:* keep A6/A9 exactly as M2a-2 defined them (Decision 12), and add two **menu runs** to a new `make osi-menu` target, both deterministic (D3) with intro skipped (D1):
   - **M1 (main menu):** Setup + N frames, the mouse parked over entry 1 (`450,330`) for the first half and entry 2 (`450,370`) for the second (inside the F22 hit boxes; Task 1 confirms), keys `down`, `down`, `up` after activation; N = F_act (Task 2a/4) + 300.
   - **M2 (Options):** as M1 to F_act + 60; then the mouse on "Options" (`450,370`) and `LMB` press/release (OnEvent 23/25 button 1); **F_evt2** = the frame of the next `C -1 OnEvent 6` (expected about click + 38 + 601, F20; Task 1 measures it with a second `--event`, Task 4 pins it); the Options frame is **F_evt2 + 60**; then `esc` at F_evt2 + 120, `backspace` at + 180, `RMB` at + 240; the run ends at F_evt2 + 300. N is therefore about F_act + 1,060, not F_act + 360.
   - Frame numbers are written relative to F_act / F_evt2 in the plan and made absolute by Task 4 once they are pinned. *Alternative:* extend A9 to 1,200 frames. *Cost if wrong:* re-pinning digests; nothing else.
3. **`C -1` becomes live.** Host-originated engine → script calls (camera `OnEvent(6)`, mouse `OnEvent(26/23/24/25)`) write `C -1 <name> <a0>…<a9>` in natives.log and the trace's `C` line, at the position the process order (Review focus 5) gives them; the replay asserts them (D14, I6), never performs them. The camera's line carries a game handle with a reference (0x447530): `C -1 OnEvent 0010:00000006 <cam handle> G n 0010:00000000 000f:00000000 …`, and a matching `H` pair follows. `Input` and `Process` stay unlogged in natives.log, so A9's natives.log is unchanged; only the camera and mouse sources write `C -1`. *Alternative:* none sensible; the reserved form exists for this. *Cost if wrong:* a log-format revision.
4. **MOUSESPEC.** *Recommend:* `x,y@frame` sets the cursor from that frame on (client pixels at the game resolution, probe 3 S5; scale 1.0 from 0x73a0f0/0x73a0f4), `lmb+@f` / `lmb-@f` press/release (buttons 1..4 as probe 3), and **`OnEvent(26, x, y)` fires every frame** once the mouse driver process runs, as in the original. No MOUSESPEC → no mouse source (keeps A6/A9 unchanged). *Cost if wrong:* re-pinned menu digests.
5. **Render-visible natives become tier 1 in both engines.** *Recommend:* every native whose effect the menu frame renders (HUD sprite and text-object setters, `hide`/`show`, font setters, camera and fog/light setters on the path) is promoted to tier 1: both engines model the state it writes, and the `Z` snapshot (Decision 6) compares that state every frame. Pixels and the D3D state log stay C++ only, checked by Task 9's independent Python oracle. *Alternative:* model the render state in C++ only. *Cost if wrong:* a shared-misreading risk on HUD state with no second engine to catch it.
6. **`Z` snapshot record (the A9 blind spots).** *Recommend:* at the end of every frame (after the last `Process` pass) both engines write `Z <frame>` followed by sorted `Z <subsystem>.<field> <value>` lines for: every live game handle's engine reference count (`Z ref <type>:<handle> <n>`), the HUD director list (index, kind, handle, visible), each HUD sprite/text object's render fields, the camera (mode, spline handle, time, position/target as f32 bits), and native state that no native reads (`cs.playing`, the timer flags). ~~Digest mode folds `Z` lines into the frame's `D` hash.~~ Per the controller ruling below, digest mode writes a separate `Z <frame> <hash>` line and `D` lines are unchanged. *Alternative:* an end-of-run dump only. *Cost if wrong:* per-frame cost (measured in Task 10's A15 row) or a missed per-frame divergence.
7. **CheckWallCloseness (the §6.3 risk).** *Recommend:* **settle it with the owner's screenshots, do not model it** (it needs M3 collision physics). F14 names what to look for: if the original's menu shows none of the in-game HUD elements (green eyes, health circles, white lights, token), the event did not fire in frames 0–4 and the port's state is right.
