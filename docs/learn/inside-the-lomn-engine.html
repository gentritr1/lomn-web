Inside the Old Game

How LOMN stores its world, how its scripts work, and how we move it all to the browser.

The game's files

The game keeps its things in packed boxes. Some boxes hold pictures. Some hold 3D shapes. Some hold tables of numbers. We built tools that open every kind of box.
KindWhat it holds
.blkArchives. One file holds many smaller files.
.slbTables: object lists, settings, positions.
.x3D models in the DirectX format.
.dds / .tgaTextures (images on the models).
.osiCompiled scripts (see below).

Each reader was checked against a second, independent reader. Each reader also survived broken and hostile files without a crash.

Scripts and the OSI machine

The game has a small helper inside it. The helper reads a list of simple orders, like "show the menu" or "play this sound". The list is the script. We had to build our own copy of the helper that obeys the orders in exactly the same way.

Much of LOMN's logic is not in C++. It is in scripts: menus, puzzles, talking, cutscenes. The scripts are compiled to bytecode in Base.osi. A virtual machine (VM) in the game runs the bytecode one instruction at a time.

We rebuilt that VM twice:

  • in C++, for the real port;
  • in Python, as an independent reference ("oracle") for testing.

Small details matter. Example: the original reads numbers with a C library call that clips very large values. Both of our first versions wrapped them instead. Tests caught this, and now both clip.

Natives: where scripts touch the engine

Sometimes the script says "ask the engine". For example, "load the village" or "how wide is the screen?". Each of these questions is a native. We must answer each one the way the old game did.

A native is a C++ function that the script can call, like gcareadirector.loadarea. Base.osi calls 728 different native names. We sort each native into a tier:

TierRule
tier1Must be exact. Its result changes what the script does.
tier2A simpler model is fine. Its result cannot change the script's path.
stubPlaceholder. Allowed only when a test proves it is harmless.

Today the menu path uses 69 natives: 35 tier1, 34 tier2, 0 stubs, with 1,705 calls in 600 frames.

Some natives call back into the script. Example: loading an area can fire an OnEvent for some objects. These re-entrant paths caused most of our subtle bugs.

Graphics: Direct3D 8 to WebGPU

The old game talks to the graphics card in an old language. Browsers speak a new one. We wrote a translator in the middle, so the old drawing orders still work.

LOMN draws with Direct3D 8 (2000). Browsers draw with WebGPU. Our engine has a shim: a layer that takes the old-style draw calls and sends them to WebGPU. We use Google's Dawn library for WebGPU on the Mac and in the browser.

The area viewer (milestone M1b) already draws the real areas this way.

From C++ to the browser

Our code is written in C++. A special tool turns it into a form the browser can run fast. The same code also runs on the Mac, which makes testing easy.

Emscripten compiles our C++17 to WebAssembly (wasm32). We build every part twice: native (Mac) and wasm32 (browser). Tests check that both builds give byte-identical results.

The game runs on a fixed time step of 1/150 s, read from the original program's data. Fixed steps make runs repeatable, which makes them testable.

flowchart TB
  S[Base.osi scripts] --> V[OSI VM]
  V -->|calls| N[Natives]
  N --> E[Engine: files, objects, camera, HUD]
  E --> R[D3D8 shim]
  R --> W[WebGPU via Dawn]

Words to know

Bytecode
Compact instructions for a virtual machine, not for the processor.
Virtual machine
A program that runs bytecode step by step.
Native
An engine function that scripts can call.
Re-entrant
A call that starts a new script call before the first one ends.
Shim
A thin layer that makes an old interface work on a new one.
Deterministic
Same input, same output, every time.

Check yourself

Why build the script VM twice?

Two independent versions let us compare results. If they differ, one has a bug. If they agree, we have stronger (but not full) proof.

What is the difference between tier1 and tier2?

A tier1 result changes the script's behaviour, so it must be exact. A tier2 result does not change the script's path, so a simpler model is safe.

Why does a fixed time step help testing?

Every run does the same steps in the same order. So two runs can be compared line by line.
