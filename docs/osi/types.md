# OSI variant types and the native registry (canonical exe)

Generated by `tools/osi/registry.py` (`make osi-tables`) from the canonical `LEGOBionicle.exe` read as data, the decomp
corpus `gen/decomp` and `Base.osi`. It documents the type column of `data/osi/natives.json` (one row per
`ScOSISystem::RegisterFunction` call, 0x5fab30). Names, addresses and counts only; no decompiled code. The JSON file is
committed (rows in execution order, keys sorted), so consumers need no Ghidra run; `make osi-tables` regenerates it.

- **Rows:** 1056 registrations, 1049 distinct `class.func` keys (case-folded), 7 keys registered twice.
- **`types`** holds 10 entries per row: entry *i* is the declared type of argument *i* for *i* < `max`, and `null` for
  the unused slots (the binary stores 0x0f there). A declared `nothing` (0x0f below `max`) would read `"nothing"`; no row has one.
- **Row fields:** `site` is the `call RegisterFunction` address, `body` the native, `init` the function that makes the call,
  `crt_index` that function's index among the 391 `.CRT` pointers (0 = the dword at 0x76f004; null when it is not an
  initializer), `winner` whether this row is the one the map keeps, `called_by_base_osi` whether `Base.osi` has a 0x82 site
  for the case-folded key, `phase` `crt` or `scinit`.
  Rows are in execution order. Menu tagging is out of scope here (moved to M2a-2).
- **M2a-1 fields:** `ret`, `ret_class`, `default`, `sets_fpu_pc64` (section below).
- **Arguments** are `(this, class&, func&, fnptr, MAX, MIN, type0..type9)`; MAX is stored at +0xc of the 36-byte
  `RegisteredFunction` and MIN at +0xd (`RegisterFunction` 0x5fab30). Each type is a u16 at +0xe + 2i.

## Return kinds (`ret`, D11) and the precision flag (`sets_fpu_pc64`, D8')

- `ret` is the kind of the `CreateVariant` overload the native's body calls (`gen/decomp/calls.jsonl`); `none` when it
  calls none (those bodies store {0x0f, 0} themselves). No body calls overloads of two kinds. The 63 overloads are
  classified twice, from the type store in each body and from its mangled parameter in `symbols.txt`: 1 colour, 1 copy, 2 float, 45 game, 12 int, 2 string.
- `ret_class` names the game type for `game`; `copy` is `CreateVariant(ScOSIVariant)` 0x6159e0, which copies its argument.
  `default` is the per-row override of the stub return (D11): only the 3 copy-kind natives have one, `nothing`, because
  their real return is unknown until M2a-2 reads their bodies.
- Over the 1049 winners: colour 1, copy 3, float 129, game 56, int 223, none 621, string 16.
- `sets_fpu_pc64` is true when the body reaches `___dec2num` (0x65f80a: `or word [ebp-0xe], 0x300; fldcw` at
  0x65f886-0x65f88c, no restore before `ret` 0x65f8a8) in the static call graph without entering the VM: `gcscripttools.stringtofloat`.
- Game-type ids are in `data/osi/types.json` (id = 0x20 + rank below). The Beta 1.5.0 mod natives (D12) are in
  `data/osi/natives_beta150.json`, decoded from `install/mods/*.dll` read as data (`mod_registrations`). Every mod row
  has min == max, so the MAX-then-MIN order of the `OSIRegisterFunction` shim is proven from the shim's bytes
  (ijl15.dll 0x100035f7-0x1000362b), not from the data.

## Unknown literals

Type literals in the registrations that are not builtins: `unknown:0x0`.

- `unknown:0x0`: 12 slots in 10 natives, 0 of them called by `Base.osi`. It is what `GetVariantType<char*>::GetIt` (0x54a550)
  returns, i.e. a `char*` parameter. `BCLCallGameFunction` (0x6015a0) converts an argument whose type differs from the
  declared one with `ConvertVariant` (0x60b9d0); docs/osi/opcodes.md records that a target other than int, float or string is
  an error ("Requested variant conversion unimplimented"). What a script can pass for such a slot is therefore settled by
  `ConvertVariant` and the native bodies, not here; the registry only records the literal. Natives: GcMoveableObj.SetProjBoneOffset, Gc3DSound.GetListenerPositionComponent, Gc3DSound.GetListenerFrontComponent, Gc3DSound.GetListenerUpComponent, Gc3DSound.GetListenerVelocityComponent, Gc3DSound.GetPositionComponent, Gc3DSound.GetVelocityComponent, Gc3DSound.GetConeOrientationComponent, GcGraphicsOptions.SetScreenResolution, GcVectorProjectile.SetPosition.

`0x18`, `0x21` and `0x22` (listed in the task brief as possible literals) do **not** occur as a type argument in any of
the 10560 slots. In the opcode table they are opcodes (0x18 `GetMemberValueFromString`, 0x21 `GetVariableValue`, 0x22
`SetVariableValue`); as variant types 0x21 and 0x22 would lie in the game-type range, so nothing needs settling.

## Game types: the id order rule

Game-type ids are assigned from 0x20 upward, on first registration, in static-init order (`.CRT` ascending). Evidence:

- `ScOSISystem::ScOSISystem` (0x5fa750) stores 0x20 as the type counter at `this+0`; `ScOSISystem::RegisterType` (0x5fae00)
  returns the counter, inserts the name into the type map and increments the counter.
- Each class has a global `theOSIType<Class>` (u16, in `.bss`, zero until registered). Every use is `if (theOSIType<Class> == 0)
  { theOSIType<Class> = RegisterType("<Class>") }`, inlined in the initializer, or the same guard inside
  `GetVariantType<Class*>::GetIt` and `CreateVariant(Class*)`. Only the first execution of a guard registers.
- `__RunInit` (0x65f530) calls the dwords of the `.CRT` section from 0x76f004 upward until a zero dword. The section is a zero
  dword at 0x76f000 (skipped), 391 initializer pointers with no zero between them, and a terminating zero, so all 391 run, in
  ascending order (checked by `crt_layout`). `_WinMainCRTStartup` (0x6565d0) calls `__RunInit` and only then `_WinMain@16`.
- The order was derived twice: from the decompiled statements of every initializer, and from the raw bytes alone (each
  `call RegisterType` is followed by `mov [theOSIType<Class>], ax`; each lazy `GetIt` is a known address). Both give the list below.
- The numeric id of a type is therefore `0x20 + (its position below)`, provided no `RegisterType` call runs earlier than
  the first initializer. That condition is derived from the static order, not observed: the exe was never run. The
  registry stores type NAMES, never numeric ids.

## Duplicates

7 keys are registered twice (all `GcHudSprite`), each time by a different body, from the initializers 0x5277d0 (`.CRT` index 227)
and 0x536910 (index 242).

**Winner: the first registration in execution order, i.e. the lower `.CRT` index.** Evidence:

- `ScOSISystem::RegisterFunction` (0x5fab30) allocates a 36-byte `RegisteredFunction`, builds the key (the two name tokens,
  `GetToken` 0x5faae0, case-folded) and calls `__tree<...>::insert_one` (0x5fb290) on the function map. The call at
  0x5fac1f is followed directly by the epilogue: the result is ignored and a refused insert leaks the new object.
- `insert_one` descends the tree, keeps the last node not ordered after the key, and compares that node with the key
  once more (0x5fb2f4-0x5fb30e). When the node's key is not less than the new key, it stores that EXISTING node and the byte at
  0x74d66c (value 0 in the file) at 0x5fb344-0x5fb355 and returns without inserting. Only otherwise does it call
  `insert_node_at` (0x5fbcb0) and store the byte at 0x74d668 (value 1). It is a unique-key insert that never overwrites.
- So the earlier registration stays and the later one is dead. `winner` is true for the first row of each key in execution
  order (`.CRT` ascending, then statement order, then the `ScInitFunc` callback). Both rows are kept in the registry.
- Key equality is equality of the token pair: the 1049 distinct keys have 1049 distinct token pairs, so no two different names
  collide.

## Registrations outside the `.CRT` initializers

2 rows (Debug.Print, Debug.Assert) are registered by the callback 0x61d6a0. `ScInitFunc::ScInitFunc` (0x4e0260) only queues it, from the initializer
0x61d7c0; `SrInitializeAll` (0x4e02c0) calls each queued callback with argument 0 (the callback registers only when its
argument is 0), and `_WinMain@16` (0x401020) calls `SrInitializeAll` before `AppMain`, i.e. after every `.CRT` initializer. Their
`crt_index` is `null` and their `phase` is `scinit`. Their order relative to the `.CRT` rows cannot matter: both keys are unique.

## Not statically determinable

- **Run-time registration through `CreateVariant`.** 45 `CreateVariant(Class*)` overloads carry the lazy guard (the others wrap
  builtins). If a native returns an object of a class whose global is still zero at that moment, the class is registered then,
  with the next counter value. Here every one of the 45 classes is already registered by an initializer (the sets are equal),
  so `CreateVariant` never assigns an id in practice; this is an inference from the static order, UNVERIFIED at run time.
- **Anything reaching `RegisterType` outside the replay.** The replay reads each initializer's own statements and the `GetIt`
  table. The accounting above finds no `RegisterType` call site other than those two kinds and `CreateVariant`, so a type could
  only be registered earlier than modelled by running a `GetIt` or `CreateVariant` from code that is not an initializer.
- **Numeric ids.** Never executed; see the order rule. Consumers must key on names and replay the order themselves.
- **Type 0 and the by-reference box.** Whether the 12 `unknown:0x0` slots can ever be satisfied is decided by `ConvertVariant`
  and the natives' bodies, not by this table.
